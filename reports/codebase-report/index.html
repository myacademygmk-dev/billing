Fixed AUTH-01: Unclaimed accounts can be taken over using an email address

Evidence: Reproduced before the fix; regression-tested after it. Status: Resolved on 2026-09-06.

Reproduction: Create a passwordless staff account, then submit its email and a new password to the public setup-password endpoint without authentication.

Previous impact: Setup returned 200 and login with the chosen password returned 200. No invitation secret or proof of email ownership was required.

Expected / acceptance: Require a single-use, expiring invitation or verified ownership before setting a password; reject email-only claims.

Resolution: Admin-only account creation now returns a private invitation with a configurable expiry (24 hours by default), pending accounts support admin-only reissue that revokes older links, and password setup requires an invitation of the exact token type. An atomic versioned pending-to-active update enforces a single winner. Email-only, expired, malformed, wrong-type, superseded, replayed and deleted-account claims are rejected.

Verification: Focused auth/savings tests: 38 passed. Latest full backend suite: 101 passed, 2 PostgreSQL-only tests skipped under SQLite. Frontend tests: 11 passed. Frontend lint and production build completed; existing unrelated lint warnings remain. Atomic invitation concurrency was source-reviewed but not exercised against live PostgreSQL.

Fixed BILL-02: Reversal amount and month allocation can disagree

Evidence: Reproduced before the fix; regression-tested after it. Status: Resolved on 2026-09-06.

Reproduction: Reverse a 500 payment for amount 1, or request amount 1000. Separately reverse a reversal.

Previous impact: Partial reversal returned -1 and released the full month; over-reversal returned -1000. Reversing a reversal produced a positive payment without restoring paid periods, permitting recollection.

Expected / acceptance: Define supported reversal semantics, enforce amount bounds, preserve allocations and prevent duplicate or unsupported reversals. Test concurrent requests on PostgreSQL.

Resolution: Reversals are now full-only. Any caller-supplied amount is rejected, only positive original payments can be reversed, the correction always equals the exact negative original amount, and all allocations are released in the same transaction. PostgreSQL row locks serialize competing requests, so only one reversal can win. The UI no longer offers or sends a partial amount.

Verification: Tests cover partial, equal and over-amount requests, reversal-of-reversal rejection, duplicate reversal rejection, full multi-month cancellation, allocation release/recollection, forged marker notes, maximum-length reasons and the frontend request body. Both PostgreSQL races (reversal/reversal and create/reversal) passed against a disposable local database. Full backend suite: 101 passed, 2 PostgreSQL-only tests skipped under SQLite; frontend: 11 passed; lint and production build completed with existing unrelated warnings.

Fixed BILL-03: Academic rollover drops ordinary unpaid arrears

Evidence: Reproduced before the fix; regression-tested after it. Status: Resolved on 2026-09-06.

Reproduction: Roll a fully unpaid student at 500/month from May 2026-April 2027 into the next year with carry_forward_arrears enabled.

Previous impact: The response reported arrears_created=0 and arrears_amount=0. Arrears calculation counted stored unpaid rows, but ordinary unpaid months have no stored rows.

Expected / acceptance: Calculate all unpaid months in the source billing range before changing the student batch; preserve and test the carried balance.

Resolution: Rollover now selects only students assigned to the source academic year (with an exact source-batch fallback for legacy rows that have no year ID), materializes each student's complete source billing overview before changing the class, batch or billing window, then carries its pending amount. A fully unpaid May-April year at 500/month creates 6000 arrears; two paid months reduce the carried amount to 5000. Arrears timestamps also use portable Python and SQL defaults so the record persists on both PostgreSQL and SQLite.

Verification: Focused rollover and payment tests: 21 passed, 2 PostgreSQL-only tests skipped under SQLite; both skipped races passed separately on PostgreSQL. Full backend suite: 101 passed, 2 skipped. Full-unpaid and partially-paid balances are asserted in the API response and persisted student_arrears row, and a same-class student from another year is verified unchanged.

P1 AUTH-03: Expired-token retries fail for requests with a body

Evidence: Source-confirmed. Status: Open; application fix not implemented.

Reproduction: Submit a POST, PATCH or PUT with an expired access token while the refresh token remains valid.

Actual / impact: The proxy consumes req.arrayBuffer() on its first attempt and reads the same consumed body again after refresh. The retried request can throw instead of completing.

Expected / acceptance: Buffer the request body once and reuse it for the authenticated retry; cover collection and save requests.

Fixed BILL-04: Assigned discounts do not affect collection

Evidence: Source-confirmed before the fix; regression-tested after it. Status: Resolved on 2026-09-06.

Reproduction: Assign a student discount, then calculate or collect that student's monthly fee.

Previous impact: Discount assignments were stored, but billing read StudentFee.expected_fee_amount without consuming StudentDiscount. Fee structures had a separate rollover application path.

Expected / acceptance: Connect agreed discount rules to payable amounts and reports; verify rounding and historical fee behavior.

Resolution: Billing now calculates monthly payable fees through assigned student discounts, applying percentage discounts against the gross monthly fee, subtracting fixed discounts, rounding once to cents, and clamping at zero. Payment collection and billing overview use the discounted helper, and report queries apply equivalent SQL discount calculations.

Verification: Focused discount tests passed: tests/test_discounts.py verified reduced collection amount, balances, reports, rounding, clamping, duplicate guards, removal, and inactive-discount assignment behavior.

Fixed IMPORT-01: Malformed optional DOB can abort a non-atomic import

Evidence: Source-confirmed before the fix; regression-tested after it. Status: Resolved on 2026-09-06.

Reproduction: Import a workbook with an invalid mapped date of birth and atomic=false.

Previous impact: DOB conversion could raise outside row-level handling; the outer handler rolled back and rethrew instead of returning a row error.

Expected / acceptance: Validate each row before persistence and return row-specific errors; ensure valid rows survive a non-atomic import.

Resolution: Optional DOB parsing is now inside the row validation path. Invalid DOB values append a row-specific date_of_birth must be a valid date error and continue when atomic=false; atomic=true still rolls back the whole import if any row error exists.

Verification: Focused student import tests passed for both non-atomic survival of valid rows and atomic rollback on invalid DOB.
