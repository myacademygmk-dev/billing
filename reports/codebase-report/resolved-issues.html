ResolvedAUTH-01: Unclaimed accounts could be taken over using an email address

Original evidence: Reproduced. The former public setup endpoint accepted a pending account's email and a caller-chosen password without proving ownership.

Acceptance: Require a single-use, expiring invitation or verified ownership before setting a password; reject email-only claims.

Implemented: Admin-only account creation now issues a signed, time-limited invitation. Password setup accepts only an invitation token and password, checks the exact token type and account version, and atomically transitions the account from pending to active. Reissuing an invitation invalidates the previous link. The frontend keeps the secret in the URL fragment, removes it after reading, and lets administrators copy or reissue links for pending users.

Regression coverage: Email-only claims; valid setup; replay; expired, malformed and wrong-type tokens; deleted accounts; reissue authorization; old-link invalidation; login preservation; and rate limiting.

Verification: Targeted auth/savings tests passed (38); the latest full backend suite passed (101, with 2 PostgreSQL-only skips); frontend tests passed (11); lint and production build completed. Existing unrelated lint warnings remain. Atomic invitation concurrency is enforced by the conditional database update and reviewed in source; a live invitation concurrency test was not run.

Database/deployment: No schema or migration change. Optional JWT_INVITATION_EXP_HOURS controls the expiry and defaults to 24 hours.

ResolvedBILL-01: Two dates in one month produced a double charge

Original evidence: Reproduced. For a student charged 500 per month, selected_months=[2026-05-01, 2026-05-15] created a 1000 payment while allocating only one May billing period.

Acceptance: Normalize and deduplicate months before computing the amount; verify the receipt amount equals the allocated months.

Implemented: Payment creation now converts every selected date to the first day of its calendar month and deduplicates that canonical list before calculating the month count, amount, start month, database allocations, or receipt data. May 1 and May 15 therefore create one May allocation and one 500 charge.

Regression coverage: Same-month different-day inputs; arbitrary dates across two months; normalized allocation rows; amount-to-allocation equality; billing start and cycle count; receipt amount and period label; and prevention of a different-day retry for an already-paid month.

Verification: Focused payment tests for this fix passed (11); the latest full backend suite passed (101, with 2 PostgreSQL-only skips); frontend tests passed (11); frontend lint and production build completed. Existing unrelated lint warnings remain.

Database/deployment: No schema, migration, dependency, or frontend contract change. Previously-created inconsistent payments are not automatically rewritten and should be reconciled against real payment records before any correction.

ResolvedBILL-02: Reversal amount and month allocation could disagree

Original evidence: Reproduced. A caller could reverse a 500 payment by 1 or 1000 while releasing the whole allocation, and could reverse the negative correction itself.

Acceptance: Define supported reversal semantics, enforce amount bounds, preserve allocations, prevent duplicate or unsupported reversals, and test concurrent requests on PostgreSQL.

Implemented: Reversals are full-only. The API rejects every caller-supplied amount and every non-positive target, records exactly the negative original amount, locks the original payment and its allocations, and releases all allocated months atomically. The locked duplicate check permits only one winner when requests race. The dialog explains full reversal and no longer offers or transmits a partial amount.

Regression coverage: Partial, equal and excessive explicit amounts; reversal of a reversal; sequential duplicate reversal; full multi-month amount/allocation cancellation; month recollection after correction; forged marker notes; maximum-length reasons; UI copy and request body; simultaneous reversals; and a simultaneous recollection/reversal.

Verification: Focused backend tests passed (21) with two PostgreSQL-only cases skipped under SQLite; both concurrency tests separately passed against a disposable local PostgreSQL database. Full backend suite passed (101, with 2 database-specific skips). Frontend tests passed (11); lint and production build completed. Existing unrelated lint warnings and expected backend-unavailable prerender fallback logs remain.

Database/deployment: No schema or migration change. The disposable PostgreSQL test database was deleted after verification. Existing historical inconsistent reversal rows are not rewritten automatically.

ResolvedBILL-03: Academic rollover dropped ordinary unpaid arrears

Original evidence: Reproduced. A fully unpaid May-April student at 500 per month rolled over with zero arrears because ordinary unpaid months had no stored allocation rows.

Acceptance: Calculate all unpaid months in the source billing range before changing the student batch; preserve and test the carried balance.

Implemented: Rollover selects only students assigned to the requested source academic year, with an exact source-batch fallback limited to legacy rows whose year ID is null. It computes the pending amount from the complete source billing overview before mutating the student's class, batch or billing window, so missing allocation rows count as unpaid months. Arrears timestamps use portable Python and database defaults so the new record persists in PostgreSQL and SQLite.

Regression coverage: A fully unpaid 12-month source range persists 6000 arrears; paying two source months persists 5000; both tests verify the response, source academic year, stored arrears row and promoted student state. A same-class student from another academic year remains unchanged.

Verification: Focused rollover/payment tests passed (21, with 2 PostgreSQL-only skips under SQLite); both skipped race cases separately passed on PostgreSQL. Full backend suite passed (101, with 2 skips). No frontend behavior changed for this issue.

Database/deployment: No schema or migration change. Existing rollover records created before this fix are not automatically recalculated and require business-record reconciliation before correction.
